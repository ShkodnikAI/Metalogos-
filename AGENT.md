# AGENT.md — Metalogos для ИИ-агента-кодера

> Этот файл — не замена README/REFERENCE.md/ADR. Это входная точка
> **методологии**: где лежит истина по каждому классу вопроса, каких
> ошибок избегать, что значит «наряд сделан». Читать первым, до
> любой задачи.

---

## 1. Главное правило: код — источник истины, не проза

Комментарии, README, ADR **могут расходиться с реальным кодом** —
не потому что кто-то соврал, а потому что код меняется быстрее, чем
успевают обновить описание рядом. За сегодня многократно
встречалось: комментарий описывает продуманную политику, а сам код
её не реализует (пример: комментарий над `check_secret_leak`
описывал обработку `http_post`, а `SINK_FUNCTIONS` эту функцию не
содержал вообще — наряд №157). Или наоборот: код давно чинен, а ADR
всё ещё описывает старую проблему как нерешённую.

**Правило:** прежде чем действовать на основе текстового описания
чего-либо в этом проекте — **проверить фактом**: `grep` по реальному
коду, реальный прогон, реальный CI. Не «README говорит X» → «делаю
исходя из X», а «README говорит X» → «grep подтверждает X» → «делаю».

## 2. Синхронизация — самая частая собственная ошибка

**Дважды за один день (сегодня) действие предпринималось на основе
устаревшего локального чекаута**, хотя `git reset --hard
origin/main` вроде бы был вызван. Причина — предыдущий
`git fetch`/`clone` кэшировал состояние ДО того, как нужный мерж
случился, и последующий `reset --hard` фиксировал именно это
устаревшее состояние.

**Обязательная последовательность перед любой проверкой:**
```bash
git fetch origin main --force   # именно --force, именно main явно
git log origin/main -1 --format='%H %ci %s'   # посмотреть, что реально пришло
git reset --hard origin/main
git log -1 --format='%h %s'     # подтвердить совпадение с предыдущей строкой
```
Если `git fetch` выводит `xxxxx..yyyyy main -> origin/main` — это
значит ветка ДЕЙСТВИТЕЛЬНО продвинулась именно сейчас, не была уже
актуальной раньше.

## 4. Быстрый поиск по ADR — не читать все 110 подряд

`docs/adr/README.md` — индекс с номерами и темами, но для конкретного
вопроса быстрее:
```bash
grep -rl "ключевое слово" docs/adr/*.md
```
Частые темы, где решение уже принято — не переоткрывать без явного
запроса владельца:
- `Result`/`Option` вместо soft-failure → **отклонено**, `ADR-0106`
- Реальная метрика вместо mock `accuracy` для `adapt` → отложено до
  реального случая, `ADR-0112`
- VM-паритет с TW (`match`, `BlockIfElse`-выражение) → сознательно не
  реализуется без реальной нужды, `ADR-0105`
- Байткод-формат `.mbc` → `bincode` с явным лимитом размера,
  `наряд №146`

## 5. Известные типичные ошибки при работе с этим кодом

**Ложные срабатывания grep из-за неверного паттерна.** Функции/тесты
в этом проекте называются не всегда так, как интуитивно ожидается —
конвенция именования тестов часто `n<NNN>_описание` или
`naryad_<NNN>_описание.rs`, не `test_описание`. Пустой результат
`grep 'fn test_'` не значит «тестов нет» — сначала проверить реальное
содержимое файла (`cat`/`wc -l`), потом уточнять паттерн.

**`mlog check` без `--root` не резолвит импорты между файлами** —
многофайловый проект даёт ложные `undefined`. Использовать
`mlog check <file> --root <entry.mlog>`.

**Не предполагать, что сторонний тип реализует трейт** (`PartialEq`,
`Debug` и т.д.) без проверки — минимум один наряд сегодня сломался
именно на этом (`Value` не реализует `PartialEq`, тест сравнивал
напрямую).

**Локальный toolchain в песочнице может не собирать проект целиком**
(несовпадение версии `Cargo.lock`/edition) — не значит, что нельзя
проверить вообще: `rustfmt --edition 2021 <file>` и `git diff`
работают независимо от полной сборки, реальный CI — окончательный
источник истины по компиляции.

## 6. Контракт наряда — что значит «сделано»

1. Ветка → `git push` в удалённый репозиторий → **открыт PR**. Ветка,
   оставленная только локально или только запушенная без PR, не
   считается сданной, независимо от готовности кода (`ADR-0110`).
2. Каждая заявленная функция подтверждена **реальным** прогоном CI
   (не локальным `cargo test`, если есть возможность настоящего
   прогона) — блокирующие джобы зелёные на самом мерж-коммите, не на
   промежуточном.
3. Если наряд предполагает несколько отдельных изменений — один
   коммит на логический шаг, не единая свалка, если это не мешает
   резко объёму задачи.
4. Отчёт называет явные допущения и то, что осталось нерешённым — не
   выдаёт частичный результат за полный.

## 7. Что не документировано нигде централизованно, но полезно знать

- Приблизительно раз в несколько нарядов реестр `BUILTIN_REGISTRY`
  и его использование меняются структурно (наряд №170 — SSOT-
  рефакторинг) — при сомнении в том, как регистрируются билтины,
  смотреть `src/builtins/mod.rs`, не полагаться на память о старой
  структуре.
- `main` — единственная ветка правды; открытые PR могут отставать от
  неё на много коммитов, если параллельно шла другая работа —
  сверяться перед мержем, не только перед началом работы.

# ADR 0018: LSP Server (Phase 3.3)

**Date:** 2026-06-01
**Status:** accepted
**Supersedes:** —
**Superseded by:** —

## Context

METALOGOS reached Phase 3.3 of the build ladder. Phases 1–3.2 are complete:
- M1–M5 (core language features), Phase 1 (fluid types), Phase 2 (knowledge graph, sandbox/mutate)
- Phase 3.1 (CLI + REPL), Phase 3.2 (standard library with import mechanism)

Editor integration is essential for developer experience. An LSP server provides real-time diagnostics, go-to-definition, and hover — the baseline IDE features expected by any programming language.

## Decision

### 1. Separate `mlog-lsp` crate on `tower-lsp`

Create a dedicated LSP server crate (`mlog-lsp/`) as a Cargo workspace member alongside the core `metalogos` crate. `tower-lsp` was chosen because it is the de-facto standard LSP framework for Rust, with async support via tokio and full LSP 3.16 compatibility.

**Workspace structure:**
```
metalogos/              (root Cargo.toml — workspace)
  Cargo.toml            [workspace]
  src/                  (core lib + binary)
  mlog-lsp/             (LSP server)
    Cargo.toml
    src/lib.rs          (Backend + LanguageServer impl)
    src/main.rs         (stdio entry point)
    tests/              (integration tests)
  editors/vscode/       (VS Code extension manifest)
```

### 2. Span propagation in AST

LSP features require source positions. The existing AST carried no position data. We added a `Span` struct (`start_line`, `start_col`, `end_line`, `end_col`) to every declaration struct. The parser now extracts spans from pest `Pair::line_col()` at each declaration boundary.

**Impact:** Fully backward compatible — existing code only reads fields, never constructs AST nodes.

### 3. Spanned diagnostics

Added `AnalysisResultDetailed` to `semantic.rs` alongside the existing `AnalysisResult`. The new type includes `Vec<Diagnostic>` with spans, converted to LSP `Diagnostic` objects in the server.

### 4. LSP features

| Feature | Implementation |
|---------|---------------|
| **Diagnostics** | `textDocument/didOpen` and `textDocument/didChange` → parse → semantic analysis → publish diagnostics |
| **Go-to-definition** | Build symbol table from declarations; find identifier at cursor; match to declaration |
| **Hover** | Find declaration at cursor; return type signature and kind as Markdown |
| **Completion** | List all named declarations from the document |
| **Text sync** | FULL (full text on every change) |

### 5. Go-to-definition and hover strategy

Rather than adding spans to every expression node (which would require pervasive AST changes), we use a text-scanning approach: extract the word at the cursor position from the raw source text, then look it up in a symbol table built from declarations. This is correct and performant for the current language constructs.

### 6. Integration testing

LSP integration tests exercise the `Backend::parse_and_analyze()` code path — the same pipeline invoked by `didOpen`. Tests verify:
- Erroneous program → error diagnostic returned
- Clean program → no diagnostics
- Parse error → parse error diagnostic
- Multiple errors → multiple diagnostics
- Go-to-definition finds entity declarations
- Hover returns type info

### 7. VS Code extension manifest

A `package.json` extension manifest is provided for VS Code integration. It declares the `.mlog` language, a TextMate grammar for syntax highlighting, and configuration for the LSP server path and trace level.

## Consequences

### Positive
- Real-time diagnostics in any LSP-compatible editor
- Go-to-definition and hover for all named declarations
- Standard workspace structure supports future crate extraction (parser, runtime, etc.)
- Span information enables future features: rename, find-references, code actions

### Negative
- WHITESPACE is implicit in the pest grammar; span calculation depends on pest's `line_col()` which counts whitespace-separated lines. Editors may report slightly different line numbers for programs with blank lines.
- Text sync is FULL (no incremental updates) — acceptable for .mlog files which are typically < 1000 lines.

### Future
- Incremental parsing for large files
- Find all references, rename symbol
- Semantic tokens (syntax highlighting based on semantic analysis)
- Code actions (quick fixes for common errors)
- Multi-file support (cross-file imports via workspace)

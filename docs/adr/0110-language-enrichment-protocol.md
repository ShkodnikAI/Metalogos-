# ADR-0110: Протокол обогащения языка

> **Status:** Accepted  
> **Date:** 2026-08-22  
> **Decision by:** owner  
> **Related:** ADR-0106/0107/0108 (governance precedent — reject
> without demonstrated need), наряд №90 (composition-first principle),
> наряд №85 (contract-before-code lesson), наряд №92 (security-lint
> classification discipline), ADR-0105 (honest-gap-documentation
> precedent)

## Context

За один рабочий день выработалась устойчивая, повторяемая практика
принятия решений о новых возможностях языка — от «можно собрать
композицией, не нужен новый код» (наряд №90) до «семантическое
решение требует prior art и ADR прежде кода» (три вчерашних отказа).
Практика применялась многократно, но нигде не была записана как
единый процесс — только разбросана по отдельным нарядам и ADR.

Формализовано по прямому запросу владельца после разбора внешнего
дорожной карты аудита: часть предложений (расширение stdlib,
сообщения об ошибках) не требует семантических решений и может
делаться независимо; часть (система типов) требует протокола,
которого не было записано явно.

## Decision

Протокол из пяти шагов, применяется к любому будущему расширению
языка:

**Шаг 0** — если возможность собирается композицией существующих
builtins на `.mlog`, это не языковая функция, а пример/паттерн.

**Шаг 1** — разделение на механическое (устоявшийся паттерн, идёт
в реализацию) и семантическое (требует prior art + ADR прежде кода).
Критерий для семантического: решение не принимается из общих
соображений полноты — только по конкретному, воспроизводимому случаю.

**Шаг 2** — контракт прежде кода: `.mlog`-пример → golden-тест в том
же коммите → минимальная реализация.

**Шаг 3** — обязательная классификация security-lint для текстовых
входов; проверка паритета TW/VM или честная документация пробела.

**Шаг 4** — ветка, реальный CI, синхронное обновление документации,
проверка коллизий имён/номеров перед финализацией.

**Кто решает:** механическое — не требует согласования каждый раз;
семантическое — только владелец, после представления вариантов,
с ADR независимо от исхода.

## Consequences

- Текст протокола дублирован в Project Instructions («устав»,
  §9) — единственное место, реально читаемое каждой будущей сессией
  агента-строителя перед выполнением наряда. Этот ADR — версионируемая
  запись того же решения в репозитории, не замена уставу.
- Будущие наряды на новые возможности языка проверяются на
  соответствие этому протоколу перед написанием, не постфактум.

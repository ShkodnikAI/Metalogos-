# ADR-0135: Semantic cache (cache_semantic) + LRU-граница кэша ADR-0047

**Status:** Accepted
**Date:** 2026-09-12
**Naryad:** #273 (issue #309)
**Precedent:** ADR-0047 (LLM response cache — фундамент; порядок проверки сохранён), ADR-0040 (EmbeddingBackend), №272/ADR-0134 (embed + векторная инфраструктура), FOIP-003 (экономия токенов как мотивация)

## Context

Кэш ADR-0047 — точное совпадение по хэшу (effective_prompt + input). Два задокументированных ограничения: (1) семантически одинаковые запросы с разной формулировкой — промах (для FOSVED на Render free tier это прямая переплата за токены); (2) «In-memory cache grows without bound (no eviction policy beyond TTL)» — строка из Consequences самого ADR-0047.

## Decision

### D1. LRU-граница in-memory кэша

In-memory HashMap кэша ограничен `max_entries` (env `METALOGOS_LLM_CACHE_MAX`, дефолт 1000; невалидное значение — громкий warning на stderr и дефолт: опечатка в env не должна отключать границу). Эвикция по давности ИСПОЛЬЗОВАНИЯ (use = get-хит или insert; monotonic-счётчик recency), не по возрасту создания. Закрывает negative ADR-0047 — в его Consequences добавлена строка-ссылка. Поверхность ADR-0047 (SQLite-таблица `llm_cache`) не меняется: `last_used` — in-memory поле.

### D2. Semantic-режим — opt-in per-паттерн, поверх точного хэша

Опция learnable-паттерна `cache_semantic: true` + `cache_threshold: 0.92` (дефолт, диапазон (0, 1], валидация на уровне парсера — громкая ошибка). Порядок проверки ADR-0047 сохраняется: few-shot → **точный хэш** → semantic → LLM. На промахе точного хэша: `embed(input)` (SSOT-менеджер №272 — те же векторы, что у билтина `embed`), cosine-скан по SQLite-таблице `llm_cache_semantic` (key, response, embedding BLOB, dim, created_at, ttl; ленивое создание), хит при similarity ≥ threshold → возврат кэшированного ответа; промах → LLM, ответ + эмбеддинг сохраняются (INSERT OR REPLACE по ключу exact-кэша).

### D3. Границы и анти-риски

- **Только с persist**: без `memory { persist: ... }` включение `cache_semantic` — громкая ошибка конфигурации при первом вызове (in-memory векторы сознательно не храним: память/корректность). Без фичи `vec` — тоже громкая ошибка (эмбеддингов нет).
- **Ложные хиты**: порог по умолчанию высокий (0.92); opt-in per-паттерн с дефолтом false — обратно совместимо с ADR-0047; dim-рассогласование строк и запроса даёт cosine 0.0 (ниже любого порога).
- **Наблюдаемость**: semantic-хит отражается в `llm_usage()` отдельным счётчиком `cache_hits_semantic` (exact-хиты не смешиваются) и в трейсах №276 как `cache: "semantic"`.
- **TTL старше семантики**: протухшая semantic-строка не хитует (та же TTL-семантика, что у точного кэша; протухшие строки удаляются при скане).
- **Full-scan cosine, не vec0**: таблица кэша мала (сотни записей), полный скан с decode BLOB и скалярным cosine — миллисекунды; KNN-инфраструктура №272 остаётся фундаментом Phase 4 памяти. Решение пересматривается при росте таблиц кэша.
- **TF-IDF-дрейф**: IDF/размерность зависят от истории embed-вызовов процесса (ADR-0040 boundary) — сходство перефразировок меняется от замера к замеру; порог — не гарантированная метрика качества, а отсечка. Честно задокументировано в REFERENCE и тестах (граничные 0.919/0.921 против дрейфа не воспроизводимы; контракт hit ⟺ sim ≥ threshold покрыт парой «низкий порог → хит» / «0.99 → промах»).
- **VM-граница**: кэш-контур ADR-0047/0135 — домен TW-интерпретатора (Files-список наряда); VM::call_llm — отдельная поверхность без кэша (дореестровая граница ADR-0105), расширение вне скоупа №273.

## Consequences

- Положительные: семантические хиты экономят токены (FOIP-003); negative ADR-0047 о неограниченном росте закрыт; наблюдаемость разделяет exact/semantic хиты; обратная совместимость полная (дефолты false / 0.92 / без persist — поведение ADR-0047 не меняется).
- Отрицательные: ложный хит возможен при завышенной близости формулировок — смягчается высоким порогом и opt-in; полный скан таблицы — O(n) на промах (приемлемо для кэш-масштабов).
- Нейтральные: semantic-таблица живёт в том же persist-файле, что и `llm_cache`/`memories` — один SQLite-файл памяти (ADR-0116 не нарушается).

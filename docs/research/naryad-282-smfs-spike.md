## 1. Постановка и сверка фактов по коду (AGENTS.md §1)

- **Песочница-гейт** (`src/interpreter/execution.rs`, Phase 7.5): `forbidden=["filesystem"]` отсекает шесть файловых builtins в двух из ТРЁХ точек builtin-диспетчеризации — см. §5 (находка).

## 2. Прототип (ветка спайка)

Виртуальное read-only пространство `sm:` поверх kv-памяти; доступ — **штатными** файловыми builtins, перехват в `src/builtins/io.rs` **до** `sandbox_path`:

| Путь | Операция | Результат |
|---|---|---|
| `sm:` | `list_dir` | db-файлы корня песочницы, содержащие таблицу `kv_store` (скан ≤512 файлов, sorted) |
| `sm:<db>` | `list_dir` | контейнеры БД (`SELECT DISTINCT`, sorted) |
| `sm:<db>/<container>` | `list_dir` | `profile.md` + бакеты с суффиксом `/` |
| `sm:<db>/<container>/profile.md` | `read_file` | детерминированный дайджест: ключи + первые 160 символов значения + `(full: sm:...)`-указатели; пустые секции не рендерятся |
| `sm:<db>/<container>/<bucket>/<key>` | `read_file` | полное значение записи (байт-в-байт); отсутствующая — мягко `""` (№254-контракт) |
| любой `sm:*` | `write_file`/`append_file`/`delete_file` | громко `[SMFS_READ_ONLY]` |

Свойства, закрывающие вопросы спайка:

- **Без расширения песочницы**: виртуальные пути не касаются диска вообще (кроме открытия БД профиля — штатный `sandbox_path_ex(ForRead)`); гейт активной песочницы `forbidden=["filesystem"]` стоит ДО перехвата (тест `sandbox_forbidden_filesystem_beats_smfs`).
- **Резервация префикса в обе стороны**: путь с `sm:` обрабатывается только виртуально — реальные файлы `sm:*` через builtins недостижимы и несоздаваемы (тест). `..` — громко `[SANDBOX_VIOLATION]`; пустые компоненты / `:` в контейнере / не-`profile.md` третья компонента / глубже 4 — громко `[SMFS_BAD_PATH]`.
- **Детерминизм**: рендер — один SQLite-запрос + форматирование, БЕЗ LLM; кэш №281 переиспользуется.
- **Реестр не расширен** (404 builtin без изменений), арности file-builtins не менялись — прототип невидим для bytecode-индексов.

## 3. Замеры (Go-критерий)

Демо-контейнер `demo`: 20 записей в 4 бакетах (`static`/`dynamic`/`notes`/`projects`), значения 500–1200 символов (~850 среднее). Путь «обход всех файлов» — полный текст всех 20 записей; путь SMFS — `cat profile.md` + 2 точечных чтения интересующих записей. Токены ≈ chars/4 (прокси без токенизатора — задокументировано честно; критерий сформулирован в отношении сокращения объёма контекста).

```
[smfs-demo] records=20, traversal=17068 chars (~4267 tokens),
            smfs(profile.md + 2 reads)=4665 chars (~1166 tokens),
            reduction=3.66x
[smfs-demo] profile.md = 4164 chars
```

**Go-критерий «сокращение ≥ 2×»: PASS (3.66×)** — согласуется с заявленными SMFS «3× меньше токенов» на Claude. Зависимость от профиля данных: чем длиннее записи, тем больше выигрыш (обрезка 160 симв); на коротких записях (<160 симв) выигрыша нет — профиль почти равен обходу. Это честная граница: SMFS-выигрыш существует там, где память состоит из содержательных (длинных) записей.

**Go-критерий «штатные builtins без расширения песочницы»: PASS** — `read_file`/`list_dir`/`file_exists` работают поверх `sm:` без изменений сигнатур и без нового транспорта; песочничный путь диска не задействован.

## 4. Ответы на вопросы спайка (issue #331)

### 4.1. Семантика записи в memory-path

В прототипе монтирование **read-only**: запись через файловые builtins громко отвергается (`[SMFS_READ_ONLY]`). SMFS-семантика «запись в memory-path генерирует воспоминание» для Metalogos избыточна и опасна: запись в память уже существует (`memorize`/`kv_set`) с готовыми границами (taint-контур №274, кэш-инвалидация №281, ledger забывания №280); второй writer через `write_file` создал бы двойной канал с расщеплёнными инвариантами. Ответ спайка: **чтение — ФС-нативно; запись — остаётся за memory-API**. Если продукт захочет sugar (`write_file("sm:db/c/b/k") ≡ kv_set`) — отдельный наряд с явным гейтом и инвалидацией; в Tier-3 прототип не входит. Это НЕ No-Go-критерий («требуется отдельный транспорт» относится к чтению — транспорт штатный).

### 4.2. Конфликт с песочницей (виртуальные пути ≠ реальные файлы)

Решение — **резервация префикса в обе стороны**: (1) любой путь `sm:*` обрабатывается виртуально и не доходит до диска (перехват до `sandbox_path` — нет TOCTOU-поверхности №252 по построению); (2) реальные файлы `sm:*` через builtins недостижимы и несоздаваемы — коллизия «виртуальный путь против реального файла» исключена. `..` в виртуальном пути — громко как в реальной песочнице; активная песочница `forbidden=["filesystem"]` сильнее перехвата (виртуальный доступ — тоже filesystem-доступ). Попутно см. §5: спайк вскрыл и закрыл pre-existing пробел того же гейта.

### 4.3. Taint-границы (секреты №274 не попадают в sm-файлы)

Экспорт читает те же строки БД, что и штатный `user_profile` №281 — **нового taint-канала прототип не создаёт**. Проверено: canary-маркер, записанный в kv-значение, детектируется `canary_check` и в полном чтении записи, и в дайджесте `profile.md` (тест `canary_detection_survives_smfs_export`) — детекция №284 сквозь экспорт работает. Честные границы: (а) значение, записанное в память, — plaintext в БД (существующая граница №281, не новая); (b) `redact` на sm-чтение не применяется — как и на любое `read_file` (санитайзер — у sink-ов №274, не у источников). Рекомендация ADR-0139: пометка записей, созданных из tainted-выражений, — продукт-вопрос будущего наряда.

### 4.4. Блокировка ≤ 1 чанка (ADR-0096)

Рендер профиля — синхронный, детерминированный, без LLM и без потоковой генерации: блокировка ограничена временем одного вызова builtin (SQLite-запрос + форматирование — миллисекунды на демо-корпусе). Контур ADR-0096 (spawn_blocking роутов) не задействуется для sm-чтений; если в продукте появится LLM-сводка профиля (настоящая «чтение-генерация») — она обязана пойти через стриминговый контур №275 и remain bounded-per-chunk; это отдельный ADR-вопрос, вне спайка.

## 5. Находка спайка: пробел sandbox-гейта (pre-existing; громко)

Рекогносцировка теста «активная песочница сильнее перехвата» вскрыла **pre-existing пробел Phase 7.5**: из трёх точек builtin-диспетчеризации интерпретатора точка вызовов ВНУТРИ выражений (`eval_expr_with_env` → `Expr::FnCall` — `let x = read_file(...)`, аргументы, return) **не имела** filesystem-гейта — `sandbox forbidden=["filesystem"]` обходился любым файловым вызовом в выражении (invoke- и ModuleAccess-пути были загейчены). Фикс — выравнивание гейта (коммит `64e0a56` на спайк-ветке) + тест. Честная пометка: в main фикс попадает только вместе с решением владельца (спайк-ветка не мержится) — рекомендован фоллоу-ап наряд-хотфикс. 4 lint-замечания clippy vec-комбинации (`vector.rs:56` transmute, `learnable.rs` ×3) — pre-existing на main, CI их не гейтит (нет vec-clippy-джобы), к спайку отношения не имеют.

## 6. Краевые случаи (покрыты тестами, tests/naryad_282_smfs_spike.rs — 13)

- пустой контейнер: дайджест `records: 0` без секций; `file_exists` → false (контейнер существует ⟺ есть записи);
- отсутствующая запись — мягко `""` (№254-контракт); отсутствующая БД/контейнер для `list_dir` — громко;
- не-sqlite файлы и sqlite без `kv_store` не монтируются в `sm:`;
- `..`/пустые компоненты/`:`-в-контейнере/глубина>4 — громко; `read_file` директории и `list_dir` файла — громко с кодами `SMFS_IS_DIR`/`SMFS_IS_FILE`;
- резервация: `write_file("sm:real.txt")` → громко, файл на диске не появляется;
- sandbox `forbidden=["filesystem"]` блокирует и `sm:`-пути (гейт до перехвата);
- TW/VM parity: одинаковый вывод байт-в-байт (`smfs_read_is_identical_in_tw_and_vm`).

Границы прототипа (задокументированы честно): db-компонента — только файл корня песочницы (одна компонента); скан корня в `list_dir("sm:")` — прототипная навигация (в продукте — реестр смонтированных БД); digest-параметр 160 симв; токен-замер — chars/4 прокси; O-2 on_write-хуки успевают увидеть событие до громкого отказа write в `sm:` (событие на отклонённую операцию — граница).

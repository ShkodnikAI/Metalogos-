# ADR 0022: JIT Compilation via Cranelift — Phase 4.3

**Status:** Accepted
**Date:** 2026-06-01
**Phase:** 4.3

## Context

Phase 4.2 delivered a bytecode VM with full language feature coverage and modest speedup over the tree-walking interpreter (1.17x aggregate). The VM uses a stack-based dispatch loop with `enum` matching, which incurs per-instruction overhead: value cloning, branch prediction misses, and indirect dispatch through `execute_code` for pattern bodies. For programs with hot inner patterns (called thousands of times in loops), this overhead is significant.

The target architecture explicitly includes Cranelift as the JIT backend. Phase 4.3 introduces a JIT compilation layer that compiles frequently-called pure patterns to native machine code, bypassing the bytecode dispatch loop entirely.

## Decision

### Architecture

```
AST → compiler → Program → VM (interpreter)
                          │
                          ├─ Call counting per pattern
                          ├─ Threshold check (N=100)
                          ├─ Cranelift JIT compilation (if pure Float-only)
                          └─ Native code dispatch (subsequent calls)
```

### New Module: `jit.rs`

The JIT compiler wraps Cranelift's `JITModule`:

- **`JitCompiler::new(threshold)`** — Creates a Cranelift JIT module with native ISA detection via `cranelift_native::builder()`.
- **`JitCompiler::is_jit_eligible(pattern)`** — Checks if a pattern can be JIT-compiled: all params are Float, body contains only LoadLocal, Const(Float), Add, Sub, Mul, Div, Return.
- **`JitCompiler::compile_pattern(pattern)`** — Translates bytecode to Cranelift IR and emits native machine code. Returns a function pointer (`*const u8`).
- **`JitCompiler::call_jit(ptr, args)`** — Dispatches to the native code via arity-specific transmutes (supports 0–3 arguments).

### Purity Analysis (`compiler.rs`)

The compiler now marks patterns as `is_pure: bool` via `analyze_purity()`. A pattern is pure if:
1. All parameter types are `Float`
2. Body contains only: LoadLocal, Const, Add, Sub, Mul, Div, CmpGt/CmpLt/CmpGe/CmpLe/CmpEq, Return
3. No globals, no builtins, no LLM calls, no struct operations, no memory

JIT eligibility is a stricter subset of purity: additionally excludes comparison instructions (Cmp*) because Cranelift boolean-to-float conversion requires instructions not available in this Cranelift version.

### JIT Integration (`vm.rs`)

The VM now includes:
- **`jit: Option<JitCompiler>`** — Optional JIT compiler (created with `Vm::with_jit(threshold)`)
- **`call_counts: Vec<usize>`** — Per-pattern call counter, grows as patterns are registered via `RegisterPattern`
- **Hot-path detection** in two locations:
  - `CallPattern` instruction handler (main loop)
  - `invoke_step` method (flow pipeline dispatch)

The dispatch logic for each pattern call:
1. Check if JIT-compiled version exists → call native code directly
2. Increment call counter → if >= threshold, attempt JIT compilation
3. Fall through to bytecode VM execution

### CLI Changes (`main.rs`)

```
mlog run --jit <file.mlog>      # VM + JIT (threshold=100)
mlog run --jit --jit-threshold 50 <file.mlog>  # Custom threshold
mlog run --vm <file.mlog>       # VM only (existing)
mlog run <file.mlog>            # Tree-walking (existing)
```

### Cranelift Code Generation

For a pattern `Increment(n: Float) -> Float { return n + 1.0 }`, the generated Cranelift IR is:

```
function %jit_hot_Increment_1(f64) -> f64 {
block0(v0: f64):
    v1 = fconst v0  [from iconst I64 + bitcast]
    v2 = fadd v0, v1
    return v2
}
```

The key Cranelift instructions used:
- `iconst(I64, bits)` + `bitcast(F64, flags, val)` for float constants
- `fadd`, `fsub`, `fmul`, `fdiv` for arithmetic
- `return_` for function return

### Intentional Constraints

These constraints are documented and deliberate:

1. **Float-only patterns**: JIT only compiles patterns where all parameters are Float. String patterns, struct patterns, and Fluid patterns remain in the VM. Rationale: Cranelift cannot safely interact with Rust's `String` type (no GC integration).

2. **Arithmetic-only bodies**: JIT only supports Add, Sub, Mul, Div, Return. Comparisons (Cmp*) are excluded because Cranelift 0.116 requires `bint` + `select` for boolean-to-float conversion, which adds complexity without proportional benefit for the benchmark workload.

3. **No globals**: JIT-compiled patterns cannot read or write global variables. This eliminates the need for guard checks (no invalidation tracking).

4. **No side effects**: Patterns with `print`, `upper`, `lower`, or other builtins are not JIT-eligible. This ensures deterministic behavior.

5. **Learnable/adapt patterns stay in VM**: Patterns with LLM interactions or adapt mutations always execute via bytecode. These have non-deterministic behavior and I/O side effects.

6. **No guard checks**: Because JIT-compiled patterns are pure (no external dependencies), no runtime guard checks are needed. The compiled native code always produces the correct result.

## Benchmark Results

### Correctness Verification

All 13 golden test examples produce identical output across three execution modes:
- Tree-walking interpreter
- Bytecode VM (`mlog run --vm`)
- Bytecode VM + JIT (`mlog run --jit`)

### Performance: Release Mode (optimized)

| Steps | VM-only (µs) | VM+JIT (µs) | JIT Speedup vs VM |
|-------|--------------|-------------|------------------|
| 10    | 22           | 91          | 0.24x            |
| 50    | 42           | 105         | 0.40x            |
| 100   | 62           | 172         | 0.36x            |
| 500   | 246          | 291         | 0.85x            |
| 1000  | 482          | 505         | 0.95x            |

### Performance Analysis

The benchmark shows JIT is slower than VM-only for small programs but approaches parity at scale. The fixed JIT overhead (~70µs) includes:
1. `JITModule` creation (ISA detection, memory allocation for executable pages)
2. Cranelift compilation of the first hot pattern
3. `finalize_definitions()` call to make code executable

At 1000 steps, the per-step cost converges:
- VM: 0.48µs/step
- JIT: (505 - 70) / 1000 = 0.44µs/step
- **JIT is ~8% faster per-step at scale**

The crossover point where JIT breaks even is approximately 1500–2000 pattern calls. Below this threshold, the fixed compilation cost dominates.

### Why JIT Appears Slower Than Expected

Three factors contribute to the current benchmark results:

1. **Test measurement includes JIT setup**: Each `run_jit()` call creates a fresh `JitCompiler`, which involves ISA detection and executable memory allocation. In production (single process, long-running), this cost is amortized.

2. **Simple pattern bodies**: The benchmark uses `Increment(n) { return n + 1.0 }` — a single `fadd` instruction. The Cranelift-compiled version saves one branch dispatch but pays for function call setup/teardown. For patterns with more operations (5+ arithmetic instructions), JIT's advantage grows proportionally.

3. **Name-based pattern lookup**: `invoke_step` performs a linear scan through patterns by name. For programs with many patterns, this adds overhead. A future optimization would add a `HashMap<String, usize>` name-to-index cache.

## Consequences

### Positive
- **JIT compilation works end-to-end**: Cranelift correctly compiles pure Float patterns to native x86_64 code. All correctness tests pass.
- **Clean architecture**: JIT is an optional layer on top of the VM. Programs that don't enable JIT are unaffected.
- **Hot-path detection works**: Call counting correctly triggers compilation at the threshold, and subsequent calls use native code.
- **Full semantic correctness**: All 13 golden examples produce identical output across TW, VM, and JIT modes.
- **24 tests, 0 failures**: All existing tests plus 6 new JIT tests pass cleanly.

### Neutral
- **Modest performance gain in current benchmarks**: JIT provides ~8% per-step speedup at 1000 iterations, but the fixed overhead means it's net slower for programs with fewer hot calls. This is an expected result for a first JIT implementation targeting simple patterns.
- **Cranelift dependency adds ~50MB to build artifacts**: The cranelift-* crates are large. This is acceptable for a language targeting AI-native workloads where JIT performance matters.
- **Float-only restriction limits applicability**: Most METALOGOS programs mix Float and String types. Only arithmetic-heavy patterns benefit from JIT. This is documented as an intentional constraint.

### Future Work
- **Pattern name cache**: Add `HashMap<String, usize>` to VM for O(1) pattern lookup in `invoke_step`.
- **Comparison JIT support**: Use Cranelift's `bint` + `select` instructions for boolean-to-float conversion in comparison-heavy patterns.
- **VM reuse**: Allow the JIT module to persist across multiple `Vm::run()` calls within a single process.
- **JIT for multi-op patterns**: Extend eligibility to patterns with 5+ arithmetic instructions where the dispatch savings are proportionally larger.
- **Phase 4.4: Self-hosting** — Compile the METALOGOS compiler itself to bytecode and JIT-compile hot compiler passes.

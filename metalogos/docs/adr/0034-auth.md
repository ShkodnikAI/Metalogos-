# ADR-0034: Role-Based Access Control (RBAC)

**Status:** Accepted
**Date:** 2026-06-03
**Phase:** 6.5 — Authentication and Authorization

## Context

Web applications must control which users can access which resources. Fine-grained access control is essential for multi-user systems, admin panels, and API endpoints with varying privilege levels.

Metalogos needs a declarative authorization mechanism that integrates tightly with the route system and session management.

## Decision

Implement **role-based access control** via `requires=[roles]` annotations on route definitions, with a `require` expression guard inside pattern bodies.

### Route-Level Authorization

```mlog
mlogserver {
    route GET "/admin" requires=["admin"] => {
        respond status:200 body:"Admin dashboard"
    }

    route POST "/settings" requires=["user", "admin"] => {
        // Only users with role "user" OR "admin" can access
    }
}
```

1. Before executing any handler, the middleware checks `session.get("role")` against `requires`.
2. If role not in the allowed list → **403 Forbidden** + audit log entry.
3. If no `requires` is specified → route is public (no auth check).

### Pattern-Level Authorization

```mlog
pattern delete_user(id) {
    require session.get("role") == "admin"
    // ... deletion logic
}
```

`require` is a special statement. If the expression evaluates to false, execution halts with 403 and an audit event is emitted.

### Audit Logging

Every authorization failure writes to the structured audit log:
```
[AUTH] 403 route=/admin role=guest ip=192.168.1.1 time=2026-06-03T10:15:00Z
```

## Prior Art

- **Rust Axum middleware:** Route guards via `middleware::from_fn_with_state`.
- **Elixir Phoenix:** `plug :require_admin` pattern with pipeline composition.
- **Spring Security:** `@PreAuthorize("hasRole('ADMIN')")` annotations.

## Consequences

- **Positive:** Authorization is declarative — visible at the route definition, not buried in handler logic.
- **Positive:** Audit logging on 403 responses provides forensic trail for security incidents.
- **Positive:** `require` in pattern bodies enables fine-grained checks for internal operations.
- **Neutral:** Role is a single string from the session; role hierarchy (e.g., admin implies user) requires application-level logic.
- **Negative:** No attribute-based access control (ABAC) in Phase 6.5; can be added later via `requires` accepting expressions.

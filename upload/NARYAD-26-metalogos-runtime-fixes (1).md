# НАРЯД-26: Исправления и улучшения runtime Metalogos

> **Назначение:** Агент Metalogos (разработка языка/рантайма)
> **Приоритет:** P0 (критические баги) → P1 (стабильность) → P2 (удобство)
> **Дата:** 2026-06-17
> **Источник:** Реальный боевой опыт проекта fosved-v2 (production deployment на Render)
> **Текущая версия:** Metalogos v0.4.0+

---

## Контекст

В проекте fosved-v2 Metalogos v0.4.0 используется как основной runtime для обработки Telegram-вебхуков, HTTP-маршрутизации, работы с SQLite и вызовов внешних API. За время эксплуатации выявлен ряд багов и ограничений на уровне языка/рантайма, которые заставили внедрять костыли на уровне приложения (Python-прокси). Данный наряд требует исправления этих проблем в самом Metalogos.

---

## P0 — Критические баги

### 1. `http_post` / `http_get` — жёсткий таймаут 30 секунд, не конфигурируемый

**Симптом:** Любой `http_post` к LLM-провайдерам (DeepSeek, Groq, Anthropic) таймаутится через 30 секунд. LLM-вызовы на сложные промпты длятся 40–120 секунд. Рантайм возвращает ошибку, ответ теряется.

**Текущее поведение (REFERENCE.md, §4.6):**
```
http_post(url, body)           — таймаут 30с
http_post(url, body, content_type) — таймаут 30с
http_get(url)                  — таймаут 30с
```
Таймаут захардкожен. Параметра для его изменения не существует.

**Влияние:** Невозможно вызвать LLM напрямую из mlog-кода. В fosved-v2 пришлось строить внешний Python-прокси с async-паттерном: mlog вызывает `/classify` → прокси сразу возвращает "OK" → LLM работает в background thread → результат отправляется в Telegram. Это антипаттерн — язык должен уметь делать long-polling HTTP-вызовы.

**Требуемое исправление:**
- Добавить 4-й (или 5-й для варианта с headers) необязательный параметр `timeout_seconds` к `http_post` и `http_get`.
- **Новые сигнатуры:**
  ```
  http_post(url, body, timeout_seconds)                        -> String
  http_post(url, body, content_type, timeout_seconds)          -> String
  http_post(url, body, content_type, headers, timeout_seconds) -> String
  http_get(url, timeout_seconds)                               -> String
  http_get(url, headers, timeout_seconds)                      -> String
  ```
- **Значение по умолчанию:** 30 (обратная совместимость).
- **Максимальное значение:** 300 секунд (5 минут).
- При превышении таймаута — возвращать строку `"ERROR: http timeout after {N}s"` вместо паники.
- Обновить §4.6 REFERENCE.md с новыми сигнатурами и примерами.

**Пример использования после фикса:**
```mlog
let resp = http_post("https://api.deepseek.com/chat/completions", body, "application/json", 120.0)
```

### 2. Отсутствие `else if` / early return в блочных `if` внутри route-обработчиков

**Симптом:** Последовательные `if` блоки внутри route-обработчика выполняются **все независимо**, без взаимного исключения. Текст,匹配 команду `/fix abc`, выполнит тело `/fix`, а затем упадёт в фоллбэк-прокси и отправится ещё и в LLM.

**Текущее поведение (документация §3.4):**
```mlog
if x > 10.0 {
  print("big")
} else if x > 5.0 {
  print("medium")
} else {
  print("small")
}
```
Документация утверждает, что `else if` существует. На практике в контексте `mlogserver` route-обработчика последовательные `if { ... }` блоки ведут себя как независимые проверки — каждый выполняется независимо от предыдущих.

**Реальный код из fosved-v2 (app.mlog, строка 246–329):**
```mlog
if starts_with(text, "/fix ") {
  // ... обработка /fix, respond("200 ok")
}

// ... другие команды ...

// Фоллбэк — ВСЕГДА выполняется, даже если команда обработана выше:
let proxy_resp = http_post("http://127.0.0.1:4000/route?chat_id=" + chat_id, text, "text/plain")
respond("200 ok")
```

Проблема: после `respond("200 ok")` внутри `if starts_with(text, "/fix ")` выполнение **не прерывается**. Код продолжает выполняться строка за строкой, и фоллбэк-прокси получает текст `/fix abc` и пытается обработать его через LLM.

**Влияние:** Дублирование обработки, лишние LLM-вызовы, неконтролируемое поведение. Единственный текущий обходной путь — оборачивать весь последующий код в `if not starts_with(...) { ... }`, что приводит к вложенным адским условиям.

**Требуемое исправление — два варианта (на выбор реализатора):**

**Вариант A — `respond()` как early return:**
После вызова `respond()` внутри route-обработчика, выполнение текущего обработчика должно прекращаться. `respond()` должен работать как implicit return из route. Это согласуется с HTTP-семантикой — ответ отправлен, обработка завершена.

**Вариант B — явный `else if` chain:**
Обеспечить корректную работу `else if` в блочной форме внутри route-обработчиков, гарантированно пропуская последующие блоки при совпадении.

**Рекомендация:** Реализовать **оба варианта**. `respond()` как early return — это правильная семантика HTTP-обработчика. `else if` — базовая конструкция языка, которая должна работать.

**Дополнительный запрос — ключевое слово `skip` или `continue`:**
Ввести конструкцию для явного прерывания выполнения внутри route:
```mlog
route "/webhook/telegram" method=POST {
  if text == "/status" {
    // ...
    respond("200 ok")
    skip  // или return — прекратить выполнение route
  }
  // Этот код НЕ выполнится, если text == "/status"
  let proxy_resp = http_post(...)
}
```

### 3. `env("LOCKDOWN_PASSWORD")` — не документировано, поведение неясно

**Симптом:** В коде fosved-v2 (строка 168) используется:
```mlog
let lockdown_password = env("LOCKDOWN_PASSWORD")
let valid = verify_password(pwd, lockdown_password)
```
Переменная `LOCKDOWN_PASSWORD` ожидается как предхешированный пароль (hash), но:
- В REFERENCE.md §4.11 `env()` описана только как `String -> String` (или `Secret` в entity context).
- Нет документации, какие переменные окружения являются системными / зарезервированными.
- Неясно, должен ли `LOCKDOWN_PASSWORD` содержать plain text или bcrypt hash.
- `env()` внутри `db {}` блока — запрещён (по отзывам), но это нигде не задокументировано.

**Требуемое исправление:**
- Добавить в REFERENCE.md §4.11 полный список системных переменных окружения, которые Metalogos ожидает/использует (если такие есть).
- Уточнить поведение `env()` в различных контекстах (верхний уровень, `db {}`, `mlogserver {}`, внутри route).
- Добавить секцию "Reserved Environment Variables" с описанием каждой.

## P1 — Проблемы стабильности

### 4. `__replace` — недокументированная функция, используемая повсеместно

**Симптом:** В fosved-v2 `__replace()` используется для экранирования JSON-строк (десятки вызовов). Функция с двойным подчёркиванием выглядит как internal/private API, но без неё невозможно нормально работать с JSON-телами в http_post.

**Документация (§4.1):** Документирована функция `replace(s, old, new)`. Но в реальном коде используется именно `__replace`, а `replace` — нет. Возможны проблемы:
- `replace` может не работать в текущей версии (баг или отсутствие импорта).
- `__replace` может быть удалена в будущей версии без предупреждения.

**Требуемое исправление:**
- Убедиться, что `replace()` (без подчёркиваний) работает корректно и задокументирована.
- Если `__replace` — это внутренняя функция, добавить её в §4.1 как стабильную, либо обеспечить работоспособность `replace`.
- Либо: ввести `escape_json(s)` как builtin (уже есть в REFERENCE.md §4.1, но нужно убедиться, что она работает внутри mlogserver route).

### 5. Отсутствие `json_encode()` в mlogserver контексте

**Симптом:** REFERENCE.md §4.7 документирует `json_encode()`, но в текущей версии mlog v6 в контексте `mlogserver` эта функция либо отсутствует, либо находится в списке forbidden patterns. В результате все JSON-тела для `http_post` собираются ручной конкатенацией строк:

```mlog
let body = "{\"chat_id\":" + chat_id + ",\"text\":\"" + safe_msg + "\"}"
```

Это:
- Некрасиво и трудно читается.
- Источник багов (пропущенный экранирующий бэкслеш).
- Не масштабируется (сложные JSON-объекты становятся неуправляемыми).

**Требуемое исправление:**
- Обеспечить работу `json_encode()` внутри mlogserver route-обработчиков.
- Альтернативно: ввести литеральную форму JSON-объектов (как в REFERENCE.md примерах §5.6: `let headers = { "X-Custom": "value" }`).
- Уточнить статус forbidden patterns — какие именно функции запрещены и почему.

### 6. `respond()` после `if` — двойной respond без ошибки

**Симптом:** В текущем поведении Metalogos, если внутри `if` блока вызван `respond("200 ok")`, а после `if` — ещё один `respond("200 ok")`, оба выполняются без ошибки или предупреждения. Это маскирует баг #2 (отсутствие early return).

**Требуемое исправление:**
- После вызова `respond()` внутри route — прерывать выполнение (см. баг #2).
- Как минимум: выдавать warning в лог при двойном respond в одном обработчике.

### 7. `to_string(query(...))` — непредсказуемое форматирование результатов запроса

**Симптом:** Результат `query()` имеет непрозрачный тип `Query`. Для вывода в Telegram-сообщения используется `to_string(query_result)`, но форматирование непредсказуемо — могут быть скобки, запятые, лишние пробелы. Это делает вывод неподготовленным для показа пользователю.

Пример из fosved-v2:
```mlog
let total_fixes = to_string(query("SELECT COUNT(*) FROM error_patterns ...", []))
// Результат может быть "[[5]]" или "5" или "[5.0]" — зависит от внутренней реализации
```

**Требуемое исправление:**
- Добавить функцию `query_scalar(sql, params) -> String|Float` для запросов, возвращающих одно значение.
- Добавить функцию `query_row(sql, params) -> List` для запросов, возвращающих одну строку.
- Сохранить `query()` как есть для multi-row результатов, но документировать формат возвращаемого значения.
- Обновить §4.15 REFERENCE.md.

### 8. `recall()` / `memorize()` / `forget()` — нет документации по TTL-семантике

**Симптом:** В fosved-v2 используются:
```mlog
let _ = memorize("deploy_notified", 24.0)    // 24 чего? часов? секунд?
let _ = memorize("system_lockdown", 1.0)     // 1 что?
let _ = memorize("lockdown_hash", hash, 48.0) // 48? с разным числом аргументов!
let _ = forget("system_lockdown", 0)         // 0?
```

REFERENCE.md §4.9 документирует:
- `memorize(key, value)` — 2 аргумента, без TTL.
- `memorize(key, value, ttl)` — 3 аргумента, TTL в минутах.
- `forget(key)` — 1 аргумент.

Но в реальном коде вызовы отличаются от документации. Неясно:
- Единица измерения TTL в 2-аргументной форме `memorize("key", 24.0)` — это TTL или value?
- Что делает `forget(key, 0)` — второй аргумент не документирован.

**Требуемое исправление:**
- Уточнить и зафиксировать сигнатуры `memorize` / `forget` / `recall`.
- Если 2-аргументная форма `memorize(key, ttl)` сохраняет key с TTL как value=true — задокументировать это.
- Убедиться, что REFERENCE.md и runtime ведут себя одинаково.

## P2 — Улучшения качества

### 9. Нет `match` / `switch` с поддержкой `starts_with` в production

REFERENCE.md §3.4 документирует `match`:
```mlog
match command {
  "start" then { print("starting") }
  starts_with "stop" then { print("stopping") }
  else { print("unknown") }
}
```
Это идеальная конструкция для диспетчеризации команд в Telegram-боте, заменяющая десятки `if` блоков. Но если `match` не работает в mlogserver route или не поддерживает `starts_with` — нужно либо исправить, либо явно задокументировать ограничения.

**Требуемое исправление:**
- Проверить работу `match` в контексте mlogserver route-обработчиков.
- Если работает — добавить примеры использования в §4.13.
- Если нет — запланировать как отдельный наряд (P1).

---

### 10. `contains()` возвращает `Float` вместо `Bool`

REFERENCE.md §4.1:
```
contains(s, needle) — String, String -> Float — 1.0 если содержит, 0.0 если нет
```
В типизированном языке функция проверки наличия подстроки должна возвращать `Bool`, а не `Float`. Это создаёт путаницу: `if contains(s, "x")` работает благодаря неявному приведению, но семантически некорректно.

**Требуемое исправление:**
- Изменить возвращаемый тип `contains()` на `Bool`.
- Сохранить обратную совместимость (0.0/1.0 автоматически приводятся к false/true).

---

### 11. Silent failures — `let _ = ...` скрывает ошибки

Текущий паттерн `let _ = http_post(...)` или `let _ = query(...)` используется для "fire and forget" вызовов. Но он также скрывает ошибки — если http_post вернёт "ERROR: ...", это молча проигнорируется.

**Требуемое исправление (необязательное, P2):**
- Добавить опцию логирования для `let _ = ...` — например, уровень лога `warn` при non-200 ответе от http_post.
- Или: ввести явный `fire(fn_call)` — конструкцию для intentional fire-and-forget с логированием результата.

---

### 12. Дублирование CREATE TABLE на каждый запрос

В fosved-v2 `/health` и `/webhook/telegram` содержат идентичный набор `CREATE TABLE IF NOT EXISTS` (7 таблиц). Это потому что нет механизма миграций или инициализации схемы при старте.

**Требуемое исправление:**
- Поддержать блок `migrate` в `db {}` (документирован в REFERENCE.md §5.6, но непонятно, работает ли).
- Или: добавить `on_start {}` блок в `mlogserver {}` для кода, выполняемого один раз при запуске.
- Обновить документацию.
